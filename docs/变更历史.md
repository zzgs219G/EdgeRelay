# EdgeRelay 变更历史

按时间倒序。每条记「改了什么 / 为什么 / 教训」。

教训部分是重点——这个项目的历史里，模块被改坏的原因从来不是逻辑错，
而是改别处时顺手重写、或拿着局部数字当整体汇报。

---

## 2026-10-22 预览构建失败 · wrangler 3 → 4

**现象**（`docs/报错.md` 原始日志）：

```
Executing user deploy command: npx wrangler preview
✘ [ERROR] Deprecation:
  The `wrangler preview` command has been deprecated.
  Try using `wrangler dev` to to try out a worker during development.
Failed: error occurred while running deploy command
```

**根因**：`wrangler preview` 这个命令名在 v3 和 v4 里是**两个不同的东西**。

| 版本 | `wrangler preview` |
|---|---|
| 3.x | 已废弃的旧命令，调用即 `throw DeprecationError`（`cli.js:121161` 是个只会抛异常的桩） |
| 4.135.0+ | 全新的 Previews 功能（分支隔离环境），官方推荐用法 |

CF 后台 Preview command 的默认值就是 `npx wrangler preview`，而
Workers Builds **使用 `package.json` 里声明的 wrangler 版本**。项目锁的是
`^3.90.0` → 实际装 3.114.17 → 命令解析到"废弃桩" → 抛异常 →
`Failed: error occurred while running deploy command`。

命令名被官方复用了，所以后台给的默认值没错，错在本地版本太老。

**修法**：

1. `wrangler` `^3.90.0` → `^4.152.0`（Previews 要求 ≥ 4.135.0）
2. `@cloudflare/workers-types` `^4` → `^5`（wrangler 4.152 的 peer 要求
   `^5.20261019.1`，否则 `npm install` 直接 ERESOLVE 失败）
3. `@cloudflare/vitest-pool-workers` `^0.5.0` → `^0.12.0`

   为什么选 0.12 而不是最新 0.23：0.12 的 peer 是 `vitest 2.0.x - 3.2.x`，
   能**留在 vitest 2**；0.23 要求 `vitest ^4.1.0`，会把 vitest 也拖上大版本。
   升级幅度越小，行为漂移越小。已知副作用：0.12 内置的 wrangler 4.72 想要
   `workers-types ^4`，与顶层的 `^5` peer 冲突，`npm ls` 会报 invalid，
   但 `npm ci` 与 `tsc` 均正常（已实测）。

4. `wrangler.toml` 新增 `[previews]` 块（含 `[[previews.kv_namespaces]]`）

   Previews **不继承生产配置**（官方原文：*Previews do not inherit
   production settings*）。缺这块的话预览实例起来后 `env.EDGE_RELAY_KV`
   是 `undefined`，每个请求都 500——比构建失败更难排查。

5. `scripts/check-preview-config.mjs` + 接入 CI

   预览构建只在 CF 侧跑，本机（Termux 上无 workerd 二进制）无法执行
   `wrangler preview` 验证。脚本做四件事：版本 ≥ 4.135.0、有
   `[previews]` 块、KV binding 与 id 合法、`[assets]` 留在顶层。同时
   若预览与生产共用同一 KV namespace 会告警（预览写入会污染生产任务表，
   并打乱 `meta:open_count` 信号灯）。

6. CI 加 `dev` 分支（原先只监听 `main`，推 dev 完全不跑检查）

**教训**：

- **依赖版本与 compatibility_date 脱节是隐形的技术债**。这个项目
  `compatibility_date = "2026-10-19"` 很新，但 wrangler 锁在 3.x 的旧模板
  继承值上。compat date 只是运行时行为开关，跟 CLI 版本毫无关系，两者
  很容易各自漂移。
- **命令名被复用是最容易误判的一类升级**。看到 "deprecated, try
  wrangler dev" 会以为这功能没了，实际是新版本把同一个名字赋予了新语义。
  判断依据只能是**命令表的注册代码**，不能凭报错文案。
- **预览与生产共用资源是"能跑但有毒"**。为了先让预览跑起来而临时指向
  生产 KV，代价是每次预览构建都写生产任务表。宁可多一步建 namespace。

## 2026-10-21 修下载链路与 KV 额度（8 个提交）

用户报「点下载显示没有 token → 又是 GitHub 401 → 又是 KV 超额」，
一路查下来是四个独立缺陷叠在一起。逐个说。

### `1acf4a3` 产物下载走网关代理

**现象**：网页点「下载产物」，页面显示
`{"message":"API rate limit exceeded for <IP>. (But here's the good news: Authenticated requests get a higher rate limit...)"}`

**根因**：不是额度真用完了，是这条链路设计上就不可能成功。面板的下载
按钮是 `<a :href="download_url">` 直跳；当 `download_url` 是 GitHub
artifact 链接时，浏览器点下去是一次**不带 Authorization 头**的跨域请求
（`<a>` 标签无法设请求头，令牌也绝不能进浏览器），GitHub 按未认证计费
——未认证限额只有 60 次/小时/IP。

也就是说：一个网关侧能拿到的东西，因为交给浏览器直连而彻底拿不到。
报错文案还在伤口撒盐（"Authenticated requests get a higher rate limit"
——网关本来就是认证的，只是浏览器不是）。

**修法**：新增 `GET /api/artifact/:jobId`（`src/artifact_proxy.ts`），
网关带 `GITHUB_TOKEN` 取回后转发。与 `log_proxy.ts` 的日志下载完全同构
——**日志早就这么做了，产物下载却漏了这一层**。
面板按链接类型分流：R2 公开直链照旧直连（快、不耗网关流量），
GitHub artifact 链接走代理。

### `c4d9912` 补上从未配置的 R2_PUBLIC_DOMAIN + 兜底原因可观测

**现象**：APP 弹「该任务只有 GitHub Artifact 链接（需令牌）」。

**根因**：`jian_box` 的 `TaskViewModel.kt:276` 是**主动拦截**——它拿到
artifact 链接、知道自己没令牌，选择拦住而不是发必定 401 的请求。这个
行为是对的。错在网关给了它一个用不了的链接：GitHub 把注解里的域名打码成
`***/apks/xxx.apk`，网关需要 `R2_PUBLIC_DOMAIN` 才能补全，而这个值
**从未被赋值**——`wrangler.toml` 只在一段注释里写了「可选」，`[vars]`
和部署日志里都没有。

**修法**：`wrangler.toml` 补 `R2_PUBLIC_DOMAIN = "https://r2.614118.xyz"`
（非敏感值，故进 `[vars]` 而非 secret）。同时修掉最可恶的部分——
`if (!publicDomain) continue` 原本**静默跳过**，网关侧零痕迹，只有 APP
知道出错。现在 `fetchDownloadUrlFromAnnotations` 返回 `{url, reason}`，
区分三种失败，并把原因写进 `console.error` 与 `job.error`。

### `c4858e2` 修 list 额度耗尽时的自残循环

**现象**：`读取任务列表失败：KV list() limit exceeded for the day.`

**根因**：这是上一轮（`951da2c`）引入的缺陷。索引对改动前创建的任务不
存在，`/api/jobs` 走兜底 `rebuildJobIds` → 调 `list()` → 额度已耗尽、
抛错。而兜底路径**没有任何节流**，于是自续命：

```
索引没建 → 调 list → 额度耗尽、失败 → 索引还是没建 → 下一次轮询再撞一遍
```

更糟的是失败的 list 同样计入 Cloudflare 操作数（其文档明确说
"All operations incur charges"），**每次重试本身在延长故障**。

**修法**：索引重建加 10 分钟节流，时间戳存 KV 而非 isolate 内存
（内存的话每个 isolate 各记一份，CF 随时起新 isolate，「10 分钟一次」
会退化成「每 isolate 一次」，实例一多等于没节流）；`rebuildJobIds` 在调
list **之前**就记尝试时间——失败也要留痕，否则节流在最需要时失效；
降级改 200 + `notice` 而非 503，并让 `has_active` 为 false。

### `39243f5` 删掉 wrangler.toml 的 [[routes]]

**现象**：部署命令报 `Failed: error occurred while running deploy command`。

**根因**：`[[routes]] pattern = "edge-relay.wu.engineer", custom_domain = true`
要求该域名所在 zone 属于当前账号，而 `wu.engineer` 不在。每次部署都炸在
最后一步。

**这个失败特别阴险**：Worker 在 routes 之前就已上传成功（日志有
`Uploaded edge-relay`），所以命令报 Failed 时**线上代码其实已经换了**。
排障时会误以为「没部署上去」而反复重推——我因此让用户白等过一轮。

**修法**：删掉那段。生产域名 `relay.614118.xyz` 是控制台绑定的自定义域，
独立于 toml。README 4 处 API 示例也从假域名改成真域名。

### `951da2c` 根治 KV list 超额：job_id 索引

**现象**：面板 503，`KV list() limit exceeded for the day`。

**根因**：上一轮（`78451ea`）只给 cron 路径加了信号灯，**`/api/jobs` 一直
在裸调 list**。面板只要停在 Dashboard 就轮询它，15s 缓存是 isolate 级的、
跨实例形同虚设，实际轻松打出每天几千次 list。

**修法**：`meta:job_ids` 存最近 200 个 job_id（按新→旧），只在建任务时
追加。`/api/jobs` 从「1 list + N get」变成「1 get + N get」。

### `49e8d23` /500 返回真实异常 + /api/jobs 不再裸奔

**现象**：登录成功进控制台，紧跟一句「网关内部错误」。CF Observability
只记 request 行（`GET /api/jobs?limit=100` → 500），真实异常被打到另一条
日志里，用户手里没有。

**修法**：总兜底把异常消息带回响应体（能走到这里的请求都已过 checkAuth，
不构成泄漏）；`/api/jobs` 自己兜住 KV 失败，降级为 503 + 真实原因。
顺带新增 `test/dashboard_entry.test.ts`，按前端真实请求序列打。

### `3c40e06` 重建 frontend/dist

**现象**：改了 `Config.vue` 却没重新 build，而 Worker 托管的是 `dist`。

**根因**：CI 有 `check-dist.mjs` 这道门禁，但它只在远端跑。我本地没跑，
于是提交漏网，CF 静默部署了旧前端。

**教训**：改了 `frontend/src/**` 就必须 `npm --prefix frontend run build`
并 `git add frontend/dist`。这条后来每次提交前都跑了。

### `78451ea` 用信号灯消除空闲期 list

第一轮 KV 优化。给 cron 加 `meta:open_count` 信号灯，空闲时零 list。
**但只覆盖了 cron 路径，面板路径一次都没降**——这就是下一轮故障的种子。

## 这一轮的共同教训

**1. 「治标不治本」的批评是对的，而且我已经知道本是什么。**

KV 没有查询能力，而这个项目有两个查询需求（「最近 N 条」按时间倒序、
「未完结任务」过滤）。我在 KV 上手写了一个查询引擎：

| 加的东西 | 实际在模拟什么 |
|---|---|
| `job_id` 逆序时间戳 | 排序键，让 `list()` 的字典序恰好等于时间倒序 |
| `meta:open_count` | `WHERE status != 'completed'` 索引 |
| `meta:job_ids` | `ORDER BY created_at DESC` 索引 |
| 每小时 reconcile | VACUUM，修索引漂移 |
| 节流 | 限流器，因为上面这些会失败 |

**每一层都有自己的失效模式，而我一轮内连续踩了三个**（漂移、自残重试、
额度）。这不是运气差，是「在字典上建数据库」的必然结果。
`kv_store.ts` 开头原本写着「访问模式是…无复杂查询」——那个判断从一开始
就是错的，我读了却没挑战它，反而顺着错误前提一路打补丁。

真正的解是迁 D1（免费档读 500 万/天、写 10 万/天、**没有 list 这个操作**）：

```sql
SELECT * FROM jobs ORDER BY created_at DESC LIMIT 50   -- 面板
SELECT * FROM jobs WHERE status != 'completed'          -- cron
```

信号灯、索引、reconcile、节流全部可以删掉。迁移还特别便宜：任务数据有
7 天 TTL、本来是临时记录，开个空 D1 直接切即可，不需要数据迁移脚本。

**没有做的原因**：当前四道闸已把 list 压到约 20/天（额度 2%），write 单
任务 4 次（额度支撑约 250 任务/天）。额度不再是瓶颈，所以迁移的优先级
低于「先把当下修好」。但它是正确的长期答案，记在这里以免忘记。

**2. 拿局部数字当整体汇报，是这一轮最贵的错误。**

我在 `78451ea` 报告「list 从 1440 降到约 20/天」——那个数字只覆盖 cron。
面板路径一次都没降，反而因轮询更勤成为主因。用户拿着这个结论以为万事
大吉，然后继续踩坑。**报数字时必须说清它覆盖哪条路径、不覆盖哪条。**

**3. 配置缺失必须有声音。**

`R2_PUBLIC_DOMAIN` 缺了一路静默降级，只有 APP 弹一句话；`wrangler.toml`
把它写成「可选」，而它其实是硬前提。一个词的注释错误坑了很久。
现在兜底原因会进日志和任务的 `error` 字段。

**4. 前端改了就一定重新 build。**

`frontend/dist` 是 Worker 实际托管的东西，CI 的门禁只在远端跑。

**5. 「部署失败」可能代码已经上线。**

`10082` 那次，Worker 在 routes 之前就上传成功了。别看到 Failed 就重推。

## 变更历史怎么写

每条记四件套：**现象**（用户看到的原话/报错）、**根因**（不是"为什么
出错"而是"为什么会写得这样错"）、**修法**、**教训**。

根因要追到设计决策，不要停在"少了一个 if"。这一轮四个故障里有三个的
根因都是设计判断失误（KV 选型、注释写错、漏了一层代理），不是手误。

# 架构评审

评审时间：2026-10-23（基于 `dev` 分支 `9b0bacd`）

结论：**这是一个把复杂度正确外包出去的薄网关，不是"简陋"。**
它的薄是有意的、合理的；真正的问题只有三个，其中两个已在本次修掉。

---

## 一、它是什么，不是什么

### 不是「只有一个 API」

实际有 11 个接口：

| 接口 | 作用 |
|---|---|
| `POST /login` / `POST /logout` / `GET /api/session` | 会话（cookie，HttpOnly） |
| `POST /api/build` | 触发构建 |
| `GET /api/status/:jobId` | 轮询状态（APP 每 5 秒的热路径） |
| `GET /api/status/:jobId/steps` | 步骤明细（按需拉） |
| `GET /api/workflows` | 流水线列表 + inputs 元数据 |
| `GET /api/jobs` | 面板任务列表 |
| `POST /api/r2/presign` | R2 预签名上传 |
| `GET /api/log/:jobId` | 日志代理（带令牌转发） |
| `GET /api/artifact/:jobId` | 产物代理（带令牌转发） |
| `GET` / `PATCH /api/config` | 运行时配置 |
| `GET /health` | 健康检查（真实探测 KV） |

### 但「薄」是真的，且是对的

它把三件重活全部外包：

| 职责 | 外包给 | 网关做什么 |
|---|---|---|
| 构建执行 | GitHub Actions | 触发 + 轮询状态 |
| 文件存储 | Cloudflare R2 | 只签上传 URL、拼下载链接 |
| 状态存储 | Cloudflare KV | 读写任务记录 |

网关自己只做三件事：**转发、令牌保护、额度控制**。

这是正确的分工。把 GitHub Actions 的调度、APK 编译、签名搬到 Worker 上
既不可能（时间上限、CPU 限制）也没必要。**薄不是缺陷，薄是设计目标。**

## 二、真实问题清单

按严重程度排序。P0/P1/P2 已在 `9b0bacd` 修复。

### 🔴 P0：任务无归属 —— 已修复

**问题**：`jobId` 形如 `<逆序时间戳base36>-<8位随机>`，可枚举。而
`status` / `log` / `artifact` / `steps` 四个接口拿到 job 直接返回，不校验
是谁的。任何持有 `RELAY_TOKEN` 的调用方遍历 jobId 就能读到别人的任务、
产物链接与加固配置。

**修法**：引入 `Principal`（面板=管理员，令牌=SHA-256 前16位指纹），
`BuildJob.owner` 记录归属，越权一律 404（不泄漏存在性）。

**遗留**：无 `owner` 的历史任务对已认证主体可见。这是有意的——升级前
本来就能互读，改成"只有面板能读"会让上线瞬间的在途构建对 APP 全部失联。
7 天后 KV TTL 自然清空，过渡期结束。

### 🟠 P1：`apk_url` 可指向任意地址（SSRF）—— 已修复

**问题**：只校验"是 http 链接"。`apk_url` 会原样传给 GitHub 流水线，由
**GitHub Runner** 去下载。攻击者可让 Runner 打云厂商元数据地址
（`169.254.169.254`，可窃取临时凭证）、扫内网、或拉超大文件烧 Actions 分钟数。

**修法**：两级校验。配了 `R2_PUBLIC_DOMAIN` 则 host 必须一致；没配则拒绝
私网/回环/链路本地/`.internal`/`.local`。顺带收紧为必须 https。

### 🟡 P2：`build` 同步等 run_id —— 已修复

**问题**：dispatch 后同步等 `RUN_ID_WAIT_MS`（默认 4s）。请求最长挂 4 秒，
Worker 有墙钟上限；而这 4 秒对调用方毫无价值（APP 拿到 job_id 就该走了）。

**修法**：立即返回 `queued`，探测交给 `ctx.waitUntil`。三条兜底：后台探测、
`status` 读缺失回查、cron 补绑。

### 🟡 P2：无持久化任务队列

当前 `dispatch` 失败即标记任务失败，没有重试。GitHub 偶发 5xx 时只能
让用户重手动触发。

**建议**：加 Cloudflare Queues，`dispatch` 失败进队列重试 3 次（指数退避）。
**代价**：Queues 是付费功能（免费档有额度但不含在 Workers 免费里），需评估。

### 🟡 P2：无审计日志

谁在什么时候触发了什么构建，只进 Cloudflare Observability（保留期有限）。
出了问题无法回溯。

**建议**：`build` 时写一条审计记录到 KV（`audit:<时间戳>`），TTL 30 天。
**代价**：每次构建多 1 次 KV 写。当前写额度 1000/天，构建频率低，可接受。

## 三、被误判为「问题」的几件事

### 「前端 JS 后端 TS 不一致」

不是问题。Worker 原生支持 TS（esbuild 内联编译，零配置）；前端 SFC 用 JS
省掉一层构建配置。**类型安全的关键边界在 API 契约，不在语言一致。**

真正的改进点是**契约共享**：目前 `src/shared/types.ts` 里的 `BuildJob`、
`BuildRequest` 等只服务后端，前端是手写对象。若前端要 TS 化，从后端导出
类型是最高性价比的第一步。

### 「只有一个用户，要什么多租户」

对。**现在不需要做用户体系。** 但归属字段（`owner`）与 `Principal` 抽象
已经就位——将来加 `user_id` 和配额只需扩这两个，路由层不用动。
这是"花 10 分钟埋地基"与"将来重构 100 行"的区别。

## 四、KV vs D1：什么时候该换

| | KV | D1 |
|---|---|---|
| 本质 | 键值，全球边缘缓存 | SQLite，关系型 |
| 查询 | 只能精确 get / 前缀 list | 任意 SQL（WHERE/JOIN/ORDER BY/GROUP BY） |
| **list 额度** | **1000/天**（最稀缺） | 无此限制 |
| 一致性 | 最终一致（10-60s） | 强一致（单主库） |
| 延迟 | 极低（就近边缘） | 较高（回主库） |
| 免费额度 | 读10万/写1千/list1千 每天 | 500万行读/天、10万行写/天、5GB |
| 运维 | 零 schema | 需要 migration |

**当前正在用 KV 做它不擅长的事**：`meta:job_ids` 索引、`meta:open_count`
信号灯、15s 分桶缓存、120s reconcile 缓存——这一整套机制的存在，都是为了
绕开「KV list 只有 1000/天」这一条限制。

换成 D1 后，这些机制可以全部删掉：

```sql
SELECT * FROM jobs
WHERE owner = ? AND status != 'completed'
ORDER BY created_at DESC LIMIT 50;
```

一条 SQL 替代「索引 key + 信号灯 + 双层缓存」。

**但仍建议暂不上 D1**，理由：
1. 现有方案工作正常，零运维；
2. 需要 migration 管理与数据迁移；
3. 读延迟变高，对 APP 5 秒轮询的热路径不利。

**触发条件**（满足任一即考虑迁移）：
- 需要任务历史查询/统计报表（"本月成功率"）
- 任务量超过 200 条（当前索引上限）导致面板看不到旧任务
- 需要按工作流/状态筛选任务

## 五、值得保留的设计

这几处是有真价值的，改动时不要顺手"优化"掉：

1. **双通道凭证**（`RELAY_PASSWORD`/`RELAY_TOKEN` 同时接受 KV 与 env）
   用户在面板改密码打错时不会把自己锁在门外。env 是逃生舱。

2. **下载走网关代理**（`log_download` / `artifact_download`）
   `<a>` 标签无法设请求头，令牌绝不能进浏览器。交给浏览器直连等于
   撞 GitHub 未认证限额（60 次/小时/IP），一个网关能拿到的东西反而拿不到。

3. **兜底原因可观测**（`explainDownloadFailure`）
   曾经 R2 直链抓不到时静默退回 artifact 链接，网关侧零痕迹，只有 APP
   弹一句"需令牌"。把原因写进日志与任务记录，是排障成本的分水岭。

4. **薄 router + 分层 services**
   `routes/` 之间互不引用，服务层不反向依赖 HTTP 层。加一个接口 =
   一个 `routes/xxx.ts` + 一行 `case`，两边都不会膨胀。
   见 `src/STRUCTURE.md`。

5. **额度意识**
   信号灯、job_id 索引、分层缓存都是为了守住 KV 免费档。注释里记录了
   每个数字的来源（1000 list/天、1000 write/天），避免下次改动时踩回去。
